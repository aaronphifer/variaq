# VariaQ 0.5.0 Release-Hardening Report

**Document type:** Internal engineering hardening report  
**Target release:** VariaQ 0.5.0  
**Baseline release:** VariaQ 0.4.1  
**Status:** Hardening implementation complete; release operations not performed

> This document records the internal VariaQ 0.5.0 hardening process, evidence,
> decisions, residual risks, and recommendations. It is **not** a replacement
> for the public release notes in `docs/releases/v0.5.0.md`.

## Executive summary

The 0.5.0 hardening pass resolved the two issues that initially prevented a
trustworthy release candidate:

1. Package and project identity were corrected from 0.4.1 to 0.5.0, with
   consistency checks and 0.5.0 distribution artifacts.
2. Graph Partition quantum support was evaluated separately from the validity
   of its BQM lowering. The lowering remains implemented and tested, but the
   automatic penalty/search behavior was not judged reliable enough for a
   public support claim. Graph Partition was therefore removed from the
   `qaoa`, `cudaq-cpu`, and `cudaq-gpu` capability matrices for 0.5.0 and is
   retained as experimental work.

The resulting public quantum-support scope is MaxCut, Assignment, and Subset
Selection. Exact and heuristic solvers continue to support all four problem
families. The output schema remains version `1`, with new fields added without
breaking the existing contract.

## Hardening phases and outcomes

### 1. Baseline and scope review

- Confirmed that the working tree contains the intended generic BQM/QAOA 0.5.0
  milestone on top of the 0.4.1 baseline.
- Kept the pass focused on release correctness, Graph Partition support
  maturity, regression coverage, packaging, and documentation.
- Did not begin 0.6 work or add physical-QPU, remote-provider, domain-specific,
  scheduling, UI, or server features.

### 2. Version and release identity

- Updated `pyproject.toml` and `src/variaq/__init__.py` to `0.5.0`.
- Updated identity coverage so package metadata and `variaq.__version__` must
  agree.
- Added the separate public release notes at `docs/releases/v0.5.0.md`.
- Corrected the prior packaging mismatch: the recorded build output is now
  `variaq-0.5.0.tar.gz` and `variaq-0.5.0-py3-none-any.whl`.
- A clean wheel installation was recorded as reporting VariaQ 0.5.0.

### 3. BQM correctness and penalty review

- Preserved the canonical binary energy convention:

  `offset + sum(linear[i] * x_i) + sum(quadratic[i,j] * x_i * x_j)`

- Preserved source-problem optimization sense and explicit constant offsets.
- Retained canonical quadratic-pair ordering, validation, stable digests, and
  structured penalty metadata.
- Exhaustive tiny-state checks for Assignment, Subset Selection, and Graph
  Partition established that their global BQM optima map to feasible optima
  under authoritative problem evaluation.
- The review explicitly distinguished a mathematically valid BQM ground state
  from QAOA failing to sample a feasible state. This prevented search-quality
  behavior from being misreported as proof of an encoding defect.

### 4. Graph Partition investigation and support decision

- Small Graph Partition instances verified the lowering and authoritative
  decode/evaluation path.
- The larger tested instance distribution exposed unreliable default behavior:
  a random eight-node, two-partition, depth-two run could produce no feasible
  samples, while another denser instance produced feasible but suboptimal
  samples.
- The evidence was not strong enough to claim that automatic Graph Partition
  penalty/search behavior is production-ready across the declared range.
- **Decision:** use the conservative support option for 0.5.0. Keep Graph
  Partition BQM lowering and tests, but do not advertise Graph Partition for
  `qaoa`, `cudaq-cpu`, or `cudaq-gpu`.
- This is a capability-maturity decision, not a deletion of the implementation
  and not a claim that the mathematical lowering is invalid.

### 5. Cross-family and cross-backend verification

- MaxCut remained on the generic BQM path without changing the seed-42
  reference behavior.
- Assignment and Subset Selection retained public quantum support after small,
  exhaustive BQM checks and solver-path validation.
- Fixed-parameter Qiskit and CUDA-Q CPU expectations for shared BQMs were
  recorded as agreeing within floating-point tolerance, including the prior
  approximately `1e-14` MaxCut CPU agreement.
- The audit covered sign conventions, offset handling, variable-to-qubit
  mapping, quadratic-pair ordering, and shared parameter candidates.

### 6. Decode, feasibility, and result selection

- Every sampled bitstring continues through `bqm.decode_bits()` and then the
  original problem's authoritative evaluator.
- Feasible states are ranked using the source problem's objective sense rather
  than raw BQM energy alone.
- Runs retain feasibility diagnostics, including feasible and infeasible sample
  counts, best solution energy, best infeasible energy, and constraint
  violations.
- A run with no feasible sample is not reported as successful.

### 7. Resource guards and capability behavior

- Resource limits are based on the actual binary-variable/qubit count before
  simulator allocation.
- Default statevector guards remain 18 variables with a 512 MiB estimate for
  Qiskit and 18 variables with a 2 GiB estimate for CUDA-Q.
- `variaq compare quantum` consults solver capabilities rather than hardcoded
  family lists and rejects unsupported combinations before execution.
- The final 0.5.0 capability matrix is:

| Family | exact | heuristic | qaoa | cudaq-cpu | cudaq-gpu |
| --- | --- | --- | --- | --- | --- |
| MaxCut | yes | yes | yes | yes | yes |
| Assignment | yes | yes | yes | yes | yes |
| Subset Selection | yes | yes | yes | yes | yes |
| Graph Partition | yes | yes | no | no | no |

### 8. Compatibility, documentation, and packaging

- Preserved output `schema_version = "1"`; new 0.5.0 fields are additive.
- Historical run/database compatibility was recorded as verified through a
  stored MaxCut reproduction path.
- Updated the README, changelog, roadmap, BQM documentation, quantum
  optimization documentation, and public 0.5.0 release notes.
- The completed hardening record reports a passing full test suite, clean Ruff
  checks, successful 0.5.0 source/wheel builds, and a clean wheel install.
- Those expensive checks were not rerun while creating this report, so that
  this documentation-only task would modify exactly one repository file.

## Final decisions

1. **Release identity:** 0.5.0 is the correct package and milestone version.
2. **Public quantum families:** MaxCut, Assignment, and Subset Selection.
3. **Graph Partition:** lowering stays in-tree as experimental; quantum support
   is not advertised in 0.5.0.
4. **Source of truth:** decoded solutions must be validated and evaluated by the
   original problem object, never accepted solely by BQM energy.
5. **Schema:** remain on schema version `1` with additive fields.
6. **Execution scope:** local Qiskit and CUDA-Q CPU/GPU simulation only; no
   physical-QPU or remote quantum-provider support.
7. **Scientific claim:** 0.5.0 makes no quantum-advantage claim.

## Known issues and limitations

- Graph Partition automatic penalty/search behavior needs broader deterministic
  validation before it can be advertised for quantum solvers.
- A mathematically correct Graph Partition BQM can still yield zero feasible
  QAOA samples at shallow depth; feasibility rate, search depth, candidate
  quality, shot count, and numerical conditioning remain separate concerns.
- GPU calculations use `fp32` by default and may differ from CPU `fp64` results
  by more than the CPU-to-CPU tolerance.
- Statevector simulation is intentionally bounded by the 18-qubit default
  resource guards.
- The release provides no physical-QPU execution and no remote IBM, AWS, or
  D-Wave integration.

## Recommendations

### Before release

- Perform a final review of the complete working-tree diff.
- Rerun the full test, lint, format, package-build, and clean-install checks on
  the exact release candidate.
- Let hosted Linux and Windows CI validate the committed release candidate
  before tagging.
- Confirm that public capabilities and `docs/releases/v0.5.0.md` still match the
  final implementation.
- Only then create the release commit, pull request, tag, and release through the
  separately authorized release workflow.

### Follow-up work

- Expand the deterministic Graph Partition corpus across path, cycle, dense,
  clustered, and seeded-random graphs.
- Separate lowering correctness, penalty sufficiency, QAOA feasible-sample rate,
  and optimum-finding rate in future diagnostics.
- Derive and document tighter per-constraint bounds where useful, while avoiding
  penalty scales that erase the source-objective signal.
- Consider explicit user-controlled Graph Partition penalty overrides only with
  validation and persisted metadata.
- Keep Graph Partition experimental until bounded evidence supports restoring it
  to the public quantum capability matrix.
- Defer broader 0.6 analysis, reporting, scaling, and visualization work until
  the 0.5.0 release is completed.
