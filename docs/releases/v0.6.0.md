# VariaQ 0.6.0 — Campaigns, Analysis, and Reporting

Release date: TBD (release-hardening complete).

## Highlights

- **Campaign subsystem** (`variaq.campaigns`): deterministic `ExperimentCampaign`
  definitions, `CampaignPlan`, bounded `CampaignRunner`, and `CampaignStore`.
- **Analysis subsystem** (`variaq.analysis`): domain-neutral grouping, quality,
  feasibility, timing, resource, repeat, scaling, and comparison summaries.
- **Reporting** (`variaq.analysis.reports`): JSON, CSV, and Markdown exports
  with deterministic report IDs and full source-run provenance. Optional
  matplotlib plots.
- **CLI additions**: `variaq campaign plan|run|list|show`,
  `variaq analyze runs|campaign`, and `variaq report campaign`.

## What is new

### Campaigns

- `ExperimentCampaign` carries a deterministic `campaign_definition_id` derived
  from canonical definition content. Re-running the same definition produces the
  same definition ID; execution uses a distinct per-run `campaign_id`.
- `variaq campaign plan` computes exact requested run counts from
  `sizes × problem seeds × solvers × repeats` and emits warnings for unsupported
  solver/family combinations or run-count limits. Plan mode executes **no solvers**.
- `variaq campaign run` enforces `DEFAULT_MAX_RUNS = 500` unless
  `--override-max-runs` is supplied. Negative or zero overrides are rejected.
- Failed runs are isolated: one solver failure does not stop the campaign;
  successful runs persist and the campaign summary reflects accurate counts.
- Problem seeds control problem generation; solver seeds are managed per repeat
  so repeated runs solve the same generated problem, not a regenerated one.

### Analysis

- `analyze_runs` groups runs by explicit keys (`family`, `problem_id`, `solver`,
  `backend`, `status`, etc.) and produces typed `GroupSummary` records.
- Quality metrics (`best_objective`, `worst_objective`, gap %, approximation
  ratio, success-at-optimum rate) are objective-sense aware.
- Feasibility statistics use actual `feasible_sample_count` /
  `infeasible_sample_count` metadata when present; missing fields remain `null`
  rather than becoming zero.
- Timing scopes are kept distinct: wall time, solver/kernel time,
  initialization, expectation evaluation, sampling, parameter search, and warmup.
- Resource summaries extract logical/binary variables, qubits, estimated
  statevector bytes, circuit depth, and gate count; missing values remain
  unavailable.
- Scaling summaries use an explicit x metric (`problem_size`,
  `logical_variables`, `binary_variables`, `qubits`) and fall back to resource
  metadata only when the group key lacks the requested metric.
- Same-problem comparisons require an exact `problem_id` match. Classical-vs-quantum
  and Qiskit-vs-CUDA-Q comparisons warn when an exact baseline or paired data is
  missing.
- Environment-version mixing is surfaced in `environment_versions` and
  aggregated warnings so reports do not silently present heterogeneous runs as
  homogeneous.
- The analysis layer is **read-only** with respect to historical runs and problem
  records.

### Reports

- `ReportArtifact` carries a deterministic `report_id` based on sorted source run
  IDs, analysis query, and campaign ID. `generated_at` and `variaq_version` do not
  participate in report identity.
- JSON reports include full `analysis`, `source_run_ids`, and `campaign_id`.
- Markdown reports include a provenance section listing every source run ID.
- CSV exports provide stable, deterministic column ordering for `groups` and
  `scaling` tables with documented `null` representation.
- Optional plotting requires matplotlib; if it is absent, other formats still
  succeed and a structured warning is emitted.
- Export output uses safe path handling, requires `--overwrite` to replace existing
  files, and avoids path traversal from user-controlled inputs.

### Storage compatibility

- `CampaignStore` adds `campaigns` and `campaign_runs` tables lazily on first
  open. Existing `runs` and `problems` tables are untouched.
- Schema version remains `1`; old databases open additively and continue to work.
- `ExperimentRun` records remain the authoritative scientific records; campaign
  membership is a separate association.

### CLI JSON contract

All new commands support `--json` and emit the existing schema-version-`1`
envelope with `status`, `data`, and optional `warnings`. Stdout is valid JSON
only.

## Known limitations

- Campaign execution is local and sequential for 0.6.0. Parallel execution is not
  introduced.
- `graph-partition` is not advertised as quantum-supported in 0.6.0; campaign
  planning marks `qaoa` / `cudaq-*` for that family as unavailable and records
  those runs as skipped/unavailable rather than failing the whole campaign.
- Optional quantum backends require the `quantum` (Qiskit) or `cudaq` (CUDA-Q)
  extras; without them, runs persist with status `unavailable`.
- Matplotlib is optional for plots; reports without plots are complete.

## What is not in this release

- No physical QPU support.
- No Triagewall, Ollama Fleet, or bb scheduling integration.
- No web UI.
- No changes to `schema_version` (still `"1"`).

## Compatibility

- Existing VariaQ 0.5.x databases remain readable; campaign tables are added on
  demand.
- `bb-plugin-variaq` 0.4.x explicitly targets VariaQ 0.5.x. Its schema parser
  still accepts VariaQ 0.6 schema-version-`1` output, but the plugin version
  policy may reject 0.6.x until it is updated. Plugin compatibility is a separate
  milestone, not a VariaQ 0.6.0 release blocker.
