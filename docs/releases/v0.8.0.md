# VariaQ 0.8.0 — Reproducible scientific benchmarking

Release date: TBD (date added at publication).

Release identity: VariaQ 0.8.0 was prepared from the reviewed 0.8.0rc1 release
candidate (commit `551151a` on branch `release/0.8.0rc1`), where CI was green
per GitHub Actions runs 38176475192 and 38176475210. The candidate hardening
pass and its validation results are recorded separately in
[v0.8.0-hardening.md](v0.8.0-hardening.md), which remains the historical record
of the rc1 validation.

## Highlights

Per the 0.8.0 changelog entries (kept unchanged):

- Controlled scientific campaign matrices and authoritative per-instance
  quality, with conservative paired-solver measurements, variability, null
  reasons, and expanded exports.
- Responsive comparison workspace with reviewed experiment setup and local
  reproduction.
- Durable web task journal: task status persisted in additive SQLite tables
  under an OS-held single worker lock. Interrupted work retains completed
  attempts, and duplicate web requests reconnect without retries. Campaign
  attempts persist before the next solver call, with recoverable membership
  provenance.
- Capability discovery no longer executes solvers, and reads no longer select
  CUDA-Q targets.
- First-backend-call timing with explicit overlap and lazy-initialization
  scope.
- Hardening fixes: canonical stored exact references, unambiguous campaign
  slots, bounded web configuration, report symlink writes, and
  cross-origin/forged-host request handling.

## Compatibility

- Experiment, campaign, report, CLI, and API schema version remains `1`.
- SQLite changes are additive only; existing stores remain readable, and
  historical record JSON is not rewritten.
- Plugin boundary: `bb-plugin-variaq` 0.6.0 accepts stable VariaQ 0.6.x and
  VariaQ 0.8.0, preserving schema 1. Plugin release alignment is handled in
  the plugin repository.
- Python 3.12 or newer is required.

## Supported platforms

- Linux is fully validated.
- At the rc1 SHA, the Windows web suite and core Windows CI passed; Windows
  CUDA-Q and Windows plugin execution remain unverified (see
  [v0.8.0-hardening.md](v0.8.0-hardening.md)).
- CUDA-Q 0.16.x via the `[cudaq]` extra on a compatible platform/runtime.
- Qiskit 2.x via the `[quantum]` extra.

## Known limitations (carried forward truthfully)

- An in-flight solver result may be lost when the process exits; native GPU
  calls have no safe in-process cancellation while in flight.
- Cold GPU device state is unverified; `cold_start_verified` remains null.
- The web interface is a loopback-first local research boundary, not a
  hardened multi-user service.
- Histories are bounded; very large paired groups need explicit bounded
  selections in the comparison view.
- No physical QPU path exists. All quantum execution is simulation.
- Simulator results do not establish quantum advantage, performance scaling,
  or GPU speedup.

## Installation and upgrade

Use Python 3.12 or newer and an isolated environment:

```sh
python -m build
python -m pip install 'dist/variaq-0.8.0-py3-none-any.whl[web]'
variaq --version
variaq web
```

`[web]` adds the local interface; `[quantum]` adds Qiskit 2.x; `[cudaq]`
requires CUDA-Q 0.16.x and a compatible platform/runtime. Install simulator
extras only where supported. Stop the old server before upgrading and back up
SQLite, problem definitions, and reports together. Starting the web app adds a
`web_tasks` table and an adjacent `.web-worker.lock` file; do not rename or
delete that lock while a server is alive. See
[v0.8.0-hardening.md](v0.8.0-hardening.md) for execution/recovery semantics,
scientific interpretation guidance, and security boundaries.
