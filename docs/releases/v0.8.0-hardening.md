# VariaQ v0.8 candidate hardening and upgrade notes

The local candidate identifies itself as `0.8.0rc1`. No release has been published.
The recommendation is **CONDITIONAL GO for local candidate evaluation**. Linux
validation passed. Windows CI must pass before claiming Windows release readiness.
The separate BB plugin has verified Linux compatibility with this candidate on
BB 0.46 / SDK 0.6.37; its Windows execution remains unverified.

## Installation and upgrade

Use Python 3.12 or newer and an isolated environment. Build the current checkout
with `python -m build`, then install the generated wheel:

```sh
python -m venv .venv
# Activate the environment using your platform's usual command.
python -m pip install 'dist/variaq-0.8.0rc1-py3-none-any.whl[web]'
variaq --version
variaq web
```

The base package has no required third-party runtime dependencies. `[web]` adds
the local interface; `[quantum]` adds Qiskit 2.x; `[cudaq]` requires CUDA-Q 0.16.x
and a compatible platform/runtime. Install simulator extras only where supported.
Capability discovery describes imports, target discovery and device discovery;
it does not prove a solver invocation works. Driver installation is outside VariaQ.

Stop the old server before upgrading. Back up SQLite, problem definitions and
reports together while no writer is active. Scientific schema version remains 1,
and historical record JSON is not rewritten. Starting the web app adds a
`web_tasks` table and an adjacent `.web-worker.lock` file. Do not rename or delete
that lock while a server is alive. A generated historical fixture created with the
committed v0.7 store was read successfully with its record JSON unchanged; this
does not establish compatibility with every possible user database.

## Execution and recovery

Campaign attempts are persisted individually before the next solver starts.
Campaign IDs and web task IDs are recorded before saving a result. On restart,
the owner of the released OS worker lock reconciles orphan campaign memberships
and recorded task counts, then marks unfinished tasks `interrupted`.

Refreshing the browser reconnects to the saved task. Submitting the same campaign
definition again returns its existing task, including a terminal task, without
rerunning it. Repeating a reproduction request for the same source run also returns
its original task. Historical campaigns without a task journal cannot be resumed
through the web UI, because their execution state is uncertain. Inspect preserved
records before explicitly planning a new campaign with a different name. CLI
campaign reruns remain an explicit append operation.

Task failure or interruption differs from solver results. Recorded attempts have
`success`, `failed` or `unavailable` status; unsupported family/solver combinations
are counted as `skipped` without inventing records. “Completed runs” counts saved
attempts, including failures and unavailable backends. It does not mean every
attempt succeeded. Matrix or persistence failures terminate the task instead of
fabricating successful progress.

An in-flight solver result may be lost when the process exits. Native GPU calls
have no safe in-process cancellation or execution deadline. The optional
`nvidia-smi` metadata probe has a three-second timeout; that is not a solver timeout.
If a native call hangs, stop the process and inspect preserved records. No automatic
retry occurs. The lock coordinates web workers using the same database; it does
not serialize independently launched CLI jobs or unrelated native-library users.

## Scientific interpretation

Objectives are evaluated from the canonical problem and solution. A successful,
feasible exact solution can establish a reference; inconsistent exact references
produce an unknown optimum. Missing reference gaps and missing measurements remain
null, with explanations. Historical metadata does not imply current precision,
timing scope, paired identity or verified cold state.

Paired evidence requires compatible problem/configuration, repeat, seed, parameter
digest, precision and warmup controls. Reproduction preserves lineage and inputs,
but does not guarantee identical hardware timing or stochastic outcomes across
package, device or runtime versions. See [scientific methodology](../scientific-benchmarks.md).

Wall time covers the solver call and excludes persistence. Backend construction,
explicit warmup, expectation calls, parameter search and final sampling have
separate documented scopes. First-backend-evaluation time captures lazy work on
the first expectation call, and overlaps either warmup or expectation evaluation.
Parameter search also contains expectation evaluation. Do not sum overlapping
measurements. Construction timing is not proof of GPU initialization time.

Bounded local validation on Linux/Python 3.12 used Qiskit 2.5.2 and CUDA-Q
0.16.0.post1 on an RTX 4060. Forty attempts succeeded across exact, heuristic,
Qiskit, CUDA-Q CPU and CUDA-Q GPU, covering unwarmed and explicit-warmup modes.
Twenty attempts used a nontrivial four-node MaxCut instance with optimum 4; twelve
paired backend expectation observations agreed within `3.11e-15`. Twenty additional
attempts exercised a zero-optimum instance. These small ideal-simulator checks
establish bounded numerical agreement, not performance scaling, GPU speedup or
physical quantum advantage. Fresh processes do not establish a cold device or
empty driver/kernel caches; `cold_start_verified` remains null.

## Security and compatibility boundaries

The default listener is `127.0.0.1`. Local mode validates Host headers and rejects
cross-site/cross-origin browser writes. Explicit non-loopback binding warns and
retains trusted-lab behavior without authentication. Do not expose it as a public
service. Request dimension/budget guards complement run-count and state/memory
limits; the explicit run-count override can still authorize expensive work.

Imported problems are validated JSON data, not executable plugins. Reports reject
unsafe filenames and existing output symlinks; downloads enforce artifact names
and root containment. Writable local storage is trusted. These checks do not stop
a hostile local process racing filesystem operations. See [security policy](../../SECURITY.md).

The tested dependency set passes `pip check`. Qiskit and CUDA-Q have bounded major
or minor ranges, while several web dependencies have minimum-only constraints.
The current test results do not guarantee compatibility with future dependency
majors. No credentials, paid services, physical QPU jobs or driver changes were
used in this hardening pass.

The separate `bb-plugin-variaq` candidate accepts stable VariaQ 0.6.x and exact
`0.8.0rc1`, preserving schema 1. Its existing campaign analysis/report surfaces
forward `paired_solvers` evidence and expanded CSV artifacts. It targets BB 0.46
and SDK 0.6.37. Actual local tests passed against this checkout (123 tests) and
the immutable VariaQ v0.6.0 tag (22 integration tests), with bounded Qiskit and
CUDA-Q CPU/GPU candidate coverage. Type/SDK/build/package checks and live BB CLI
workflows passed. One existing SDK scanner check remains skipped for false
positives; plugin Windows execution and six development dependency advisories
remain documented limits. The production dependency audit reports zero advisories.
This is separately verified plugin compatibility, not a published plugin release.

## Validation and remaining work

The full local suite, product Ruff scope, source/wheel builds, fresh wheel installs,
historical fixture, forced-exit recovery and desktop/mobile browser flows were
verified during this pass. Browser testing included report download, reproduction,
refresh/restart recovery and accessibility scans at three viewport sizes. Whole-tree
Ruff still reports unrelated untracked research files; those files were preserved
and excluded from the source distribution.

Before a public release, run the configured Windows CI, including file-lock and
recovery tests, including the report symlink privilege portability regression.
Windows CUDA-Q and Windows plugin execution were not verified. Defer device cold-start isolation, safe
native termination, authenticated network hosting and a larger telemetry system.
The comparison view's bounded input window can split very large paired groups;
use explicit bounded selections rather than assuming it summarizes an unlimited
history. No automatic recovery execution, distributed queue or remote worker was
introduced.
